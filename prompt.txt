FOCUSSHIELD — SEPARATE APP USAGE TRACKING FROM APP-LIMIT ALLOWANCE TIMER

IMPORTANT ARCHITECTURAL CHANGE:

FocusShield currently has its own timer/session mechanism for App Limit overlay sessions.

DO NOT REMOVE, REPLACE, OR REPURPOSE that timer.

The existing FocusShield timer has a valid and different responsibility:

It represents the amount of time the user has explicitly selected/allowed from the FocusShield App Limit overlay.

Android UsageStatsManager must become the authoritative source for ACTUAL APPLICATION USAGE.

These two concepts MUST remain completely separate.

==================================================
1. TWO DIFFERENT TIME CONCEPTS
==================================================

Implement and enforce this separation:

A. ACTUAL APP USAGE
Source:
Android UsageStatsManager

Meaning:
How much time the user actually spent with an application in the foreground.

Used for:
• App Limit "Used" time
• Daily usage statistics
• Home statistics
• Analytics
• Historical usage
• Usage charts
• Cloud analytics/sync
• Calculating remaining daily app limit

B. FOCUSSHIELD ALLOWANCE / TEMPORARY SESSION
Source:
Existing FocusShield App Limit timer/session system

Meaning:
How much time the user explicitly grants themselves through the FocusShield overlay.

Used for:
• Overlay countdown
• Temporary access duration
• Remaining allowance
• Session expiration
• App-limit enforcement
• Emergency/bypass sessions
• Triggering the FocusShield blocking overlay

NEVER treat B as A.

==================================================
2. EXAMPLE
==================================================

User has:

Daily YouTube limit = 4 hours

Android UsageStatsManager reports:

YouTube actual foreground usage = 3 hours

User opens the FocusShield App Limit overlay and selects:

"30 minutes"

This means:

actualUsage = 3 hours

temporaryAllowance = 30 minutes

It does NOT mean:

actualUsage = 3h 30m

If the user actually spends only 8 minutes on YouTube during that temporary session:

actualUsage increases according to Android's actual foreground usage.

The FocusShield allowance/session timer remains an enforcement mechanism.

Do NOT add the selected 30 minutes directly to actual usage.

==================================================
3. USAGESTATSMANAGER AS THE AUTHORITY
==================================================

Use Android UsageStatsManager for the canonical "actual app usage" calculation.

Prefer:

UsageStatsManager.queryAndAggregateUsageStats()

and:

UsageStats.totalTimeInForeground

where appropriate.

Also inspect UsageEvents if required to correctly handle the currently active foreground interval.

Create/use a single repository/domain-level method for canonical usage, conceptually:

getActualUsageToday(packageName): Long

The returned value must represent actual foreground usage.

All UI and analytics that display "app used time" must ultimately use this canonical value.

==================================================
4. REMOVE DOUBLE COUNTING
==================================================

Audit and remove any architecture where:

FocusShield timer
+
UsageStatsManager
=
actual app usage

This is WRONG.

Also avoid:

maxOf(systemUsage, databaseUsage)

as a generic solution if databaseUsage may itself contain incorrectly accumulated FocusShield timer time.

Do not use the FocusShield temporary-session timer as a source for historical actual usage.

Do not add allowance/session duration directly to DailyAppUsageEntity.usedMillis.

==================================================
5. KEEP THE EXISTING FOCUSSHIELD TIMER
==================================================

The existing timer must remain functional.

It should continue controlling:

• selected access duration
• temporary App Limit sessions
• countdown UI
• session expiration
• enforcement
• emergency access
• bypass behavior

For example:

User selects 30 minutes.

FocusShield starts:

remainingAllowance = 30 minutes

The countdown may decrement while the user is actually using the protected application according to the existing enforcement design.

When the allowance reaches zero:

→ trigger existing App Limit blocking behavior.

Do NOT remove this functionality merely because UsageStatsManager is now used for actual usage statistics.

==================================================
6. SEPARATE DATA FIELDS
==================================================

Audit the existing:

DailyAppUsageEntity
AppLimitSessionEntity
AppLimitManager
AppLimitRepository
AppLimitsViewModel
DeviceUsageStatsHelper

and determine which existing fields currently mix these concepts.

Refactor where necessary so the data model has clear semantics.

Conceptually distinguish:

systemForegroundUsageMillis
    = actual usage reported by Android

temporaryAllowanceMillis
    = user-selected allowed duration

remainingAllowanceMillis
    = remaining temporary access duration

emergencyUsageMillis
    = emergency/bypass usage if applicable

enforcementState
    = local state used by App Limit enforcement

Do not necessarily create all of these fields if the existing architecture can represent them cleanly.

The important requirement is semantic separation.

==================================================
7. DAILY APP LIMIT CALCULATION
==================================================

The daily limit calculation should conceptually be:

actualUsageToday
    = UsageStatsManager actual foreground usage

remainingDailyLimit
    = dailyLimit - actualUsageToday

Example:

Daily limit = 4h
Actual Android usage = 3h

Remaining = 1h

If the user opens a FocusShield temporary session for 30 minutes, do NOT immediately change:

actualUsageToday

from 3h to 3h30m.

Only actual application foreground usage changes actualUsageToday.

==================================================
8. REAL-TIME ENFORCEMENT
==================================================

Important:

UsageStatsManager is the authoritative source for the user's actual usage statistic.

However, UsageStatsManager may not always provide instantaneous real-time updates.

Therefore, preserve the existing foreground detection/enforcement mechanism where useful for real-time App Limit enforcement.

Use:

• Accessibility foreground-package detection
• existing FocusShield timer/session logic
• UsageStatsManager

for their appropriate responsibilities.

DO NOT make the existing enforcement timer responsible for historical usage accounting.

The architecture should be:

UsageStatsManager
        ↓
actual usage calculation
        ↓
statistics / daily limit / analytics

Existing FocusShield timer
        ↓
temporary allowance
        ↓
real-time enforcement
        ↓
block overlay

==================================================
9. FOREGROUND VALIDATION
==================================================

When calculating actual usage, correctly handle:

• app enters foreground
• app leaves foreground
• switching to another application
• Home screen
• Settings
• notification shade
• keyboard/input method
• screen off
• device lock
• screen on
• split-screen
• multi-window
• floating windows
• background playback

Do not count an application simply because its process is alive.

Do not count background media playback as foreground usage.

Use Android's usage data rather than extending an internal wall-clock timer indefinitely.

==================================================
10. EXISTING DATABASE DATA
==================================================

Audit existing DailyAppUsageEntity records.

Determine whether:

usedMillis

currently contains:

A. Android system usage
B. FocusShield timer usage
C. a mixture of both

If it contains a mixture, migrate/reconcile it safely.

Do NOT blindly preserve known incorrect accumulated values.

For current-day actual usage, Android UsageStatsManager should be able to correct stale/overcounted FocusShield values.

Example:

Existing database:
YouTube = 5h

Android UsageStatsManager:
YouTube = 3h

If the 5h was produced by the old incorrect FocusShield timer accumulation, do not continue displaying 5h.

Reconcile it to the authoritative actual usage model.

Do not destroy unrelated App Limit configuration.

Analytics → database accumulator

These must all represent the same actual-usage definition.

==================================================
12. CLOUD SYNC
==================================================

Only synchronize ACTUAL APP USAGE data for analytics/statistics according to the existing Supabase architecture.

Do NOT synchronize the temporary FocusShield countdown as if it were actual application usage.

Cloud data should distinguish:

ACTUAL_USAGE / ANALYTICS

from:

LOCAL_ENFORCEMENT_STATE

Temporary enforcement state such as:

• remaining countdown
• current active overlay session
• current enforcement state

should generally remain local/device-specific unless the existing product explicitly requires otherwise.

Meaningful historical usage required for cross-device statistics should be synchronized.

==================================================
13. OFFLINE BEHAVIOR
==================================================

FocusShield must continue working offline.

If UsageStatsManager is available:

→ calculate actual usage locally.

If network is unavailable:

→ App Limit enforcement still works.

→ actual usage statistics still work.

→ cloud synchronization waits until connectivity returns.

The cloud must never be required for App Limit enforcement.
